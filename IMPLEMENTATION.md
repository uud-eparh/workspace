## 1. Введение

В этом документе описаны ключевые архитектурные и технические решения, принятые при разработке OpenLedger. Здесь собраны нестандартные подходы, которые могут быть неочевидны при первом знакомстве с кодом.

---

## 2. Аутентификация без глобального пароля

### 2.1. Проблема
Традиционно у пользователя есть один глобальный пароль для входа в систему. Но в OpenLedger у пользователя может быть доступ к нескольким компаниям с разными паролями.

### 2.2. Решение
Мы отказались от хранения пароля в `global_users`. Вместо этого пароль хранится в `membership`:
- Для каждой компании своя запись с паролем.
- Для глобального доступа (`CHIEF`) создается запись с `tenant_id = NULL`.

### 2.3. Преимущества
- Пользователь может иметь разные пароли для разных компаний.
- Один пароль = один доступ (безопаснее).
- Гибкость: можно добавить доступ к новой компании без изменения глобального пароля.

### 2.4. Недостатки
- Сложнее понять, какой пароль использовать для входа.
- Требуется явное управление глобальным доступом (для `CHIEF`).

## 3. Роль CHIEF

### 3.1. Проблема
Нужно было создать роль, которая может создавать компании, но не является суперадминистратором.

### 3.2. Решение
Добавлена глобальная роль `CHIEF` (отдельно от `USER` и `SUPER_ADMIN`).
- `CHIEF` может создавать компании.
- `CHIEF` имеет глобальный доступ (запись в `membership` с `tenant_id = NULL`).
- `CHIEF` может добавлять пользователей в свои компании.

### 3.3. Преимущества
- Четкое разделение прав.
- Суперадминистратор не связан с компаниями.
- Руководитель может делегировать управление (назначать других `CHIEF`).

---

## 4. Глобальный доступ через tenant_id = NULL

### 4.1. Проблема
Нужно было дать `CHIEF` возможность входить в систему без привязки к конкретной компании.

### 4.2. Решение
Мы использовали `tenant_id = NULL` в `membership` для обозначения глобального доступа.
- При входе с `tenant_id = NULL` пользователь попадает в "глобальный режим".
- В глобальном режиме `CHIEF` видит список своих компаний и может создавать новые.

### 4.3. Преимущества
- Единая модель данных для всех типов доступа.
- Простота реализации (одна таблица `membership`).
- Гибкость: можно добавить другие глобальные роли.

---

## 5. Генерация пароля при добавлении пользователя

### 5.1. Проблема
При добавлении пользователя в компанию нужно задать пароль. Но пользователь может быть уже добавлен в другую компанию со своим паролем.

### 5.2. Решение
Система генерирует простой пароль (8 символов) при добавлении пользователя в компанию.
- Пароль отображается один раз (в модальном окне).
- Пользователь может сменить пароль после входа.

### 5.3. Преимущества
- Безопасно (пароль не передается по незащищенным каналам).
- Удобно для администратора (не нужно придумывать пароль).
- Пользователь может установить свой пароль позже.

---

## 6. Отсутствие глобального пароля у USER

### 6.1. Проблема
У обычного пользователя (`USER`) нет глобального пароля. Он входит только в компании, куда его добавили.

### 6.2. Решение
Мы не создаем запись в `membership` с `tenant_id = NULL` для `USER`. Вход возможен только при наличии записи с `tenant_id` не NULL.

### 6.3. Преимущества
- Безопаснее (нет "лишнего" пароля).
- Четкое разделение: `USER` всегда работает внутри компании.

---

## 7. Асинхронный SQLAlchemy

### 7.1. Проблема
FastAPI поддерживает асинхронность, и мы хотели использовать ее для работы с БД.

### 7.2. Решение
Используем **async** версию SQLAlchemy:
- `create_async_engine`
- `AsyncSession`
- `async_sessionmaker`

### 7.3. Особенности
- Все запросы к БД выполняются через `await`.
- Используем `async with AsyncSessionLocal() as db:` для управления сессиями.
- Применяем `pool_pre_ping=True` для проверки соединений.

## 8. Row-Level Security (RLS)

### 8.1. Проблема
Данные разных компаний должны быть полностью изолированы.

### 8.2. Решение
Включен RLS на уровне PostgreSQL.
- Для всех таблиц с `tenant_id` созданы политики.
- Бэкенд устанавливает `app.tenant_id` через `SET` при каждом запросе.
- Если `tenant_id` не установлен, политика запрещает доступ.

### 8.3. Преимущества
- Изоляция данных гарантируется на уровне БД.
- Даже при ошибках в коде данные не перемешиваются.
- Простота реализации (политики создаются один раз).

## 9. Использование UUID вместо Integer

### 9.1. Проблема
Традиционные целочисленные ID могут быть предсказуемы и конфликтовать при объединении данных.

### 9.2. Решение
Все первичные ключи используют UUID v4 (генерация на уровне БД).
- `server_default=text("gen_random_uuid()")`

### 9.3. Преимущества
- Уникальность даже при объединении данных.
- Безопасность (ID не предсказуемы).
- Совместимость с распределенными системами.

---

## 10. JWT с tenant_id

### 10.1. Проблема
Нужно хранить информацию о текущем слое в токене.

### 10.2. Решение
В JWT-токен добавляется `tenant_id` (может быть NULL).
- При входе без слоя `tenant_id = None`.
- При входе в компанию `tenant_id = ID компании`.

### 10.3. Преимущества
- Не нужно делать запрос к БД для определения текущего слоя.
- Быстрое переключение между компаниями.
- Безопасность (токен подписан).

## 12. Ошибки и их обработка

### 12.1. Общие ошибки
- **Неверный логин или пароль** — скрыто, что именно неверно.
- **Пользователь заблокирован** — `is_active = false`.
- **Доступ к слою заблокирован** — `membership.is_active = false`.

### 12.2. Ошибки при входе
- **Один пароль для нескольких слоев** — ошибка, требующая смены пароля.

### 12.3. Ошибки при создании компании
- **Пароль уже используется** — запрет на использование одного пароля для двух компаний.
