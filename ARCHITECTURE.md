# OpenLedger — Архитектура системы

## 1. Общие принципы

### 1.1. Мультиарендность
- Система поддерживает неограниченное количество изолированных слоев учета (компаний).
- Каждый слой полностью изолирован от других.
- Пользователь может иметь доступ к нескольким слоям с разными паролями.

### 1.2. Аутентификация
- Вход по связке **логин + пароль**.
- Пароль проверяется против хешей в таблице `membership`.
- **SUPER_ADMIN** входит без слоя (глобальный доступ).
- **CHIEF** имеет глобальный доступ (без слоя) и доступ к своим компаниям.
- **USER** входит только в компании, где у него есть доступ.

### 1.3. Изоляция данных
- Данные каждого слоя изолированы с помощью RLS (Row-Level Security) в PostgreSQL.
- Все таблицы, содержащие `tenant_id`, защищены политиками RLS.

## 2. Сущности

### 2.1. Пользователь (`global_users`)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID (PK) | Уникальный идентификатор |
| `username` | String(100) | Уникальный логин |
| `email` | String(255) | Уникальный email |
| `full_name` | String(255) | ФИО |
| `department` | String(255) | Отдел |
| `subdivision` | String(255) | Подразделение |
| `role` | Enum | Глобальная роль: `SUPER_ADMIN`, `CHIEF`, `USER` |
| `is_active` | Boolean | Активен/заблокирован |

**Важно:** Один человек может иметь несколько логинов.

### 2.2. Слой учета (компания) (`tenants_layers`)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID (PK) | Уникальный идентификатор |
| `name` | String(255) | Название компании (обязательно) |
| `description` | Text | Описание (опционально) |
| `master_key_hash` | String(255) | Мастер-ключ слоя |
| `is_active` | Boolean | Активен |
| `created_by` | UUID (FK) | ID пользователя, создавшего слой |

### 2.3. Членство (`membership`)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID (PK) | Уникальный идентификатор |
| `user_id` | UUID (FK) | ID пользователя |
| `tenant_id` | UUID (FK, NULL) | ID слоя (NULL = глобальный доступ) |
| `role` | String(50) | Роль внутри слоя: `chief`, `glavbukh`, `kassa`, `sklad` |
| `layer_access_hash` | String(255) | Хеш пароля для входа |
| `is_active` | Boolean | Доступ активен |

**Особенности:**
- `tenant_id = NULL` означает глобальный доступ (без слоя).
- У одного пользователя может быть несколько записей `membership` с разными `tenant_id`.
- Один пользователь может иметь только одну запись с `tenant_id = NULL`.

## 3. Роли и права

### 3.1. Глобальные роли (в `global_users.role`)

| Роль | Описание |
|------|----------|
| `SUPER_ADMIN` | Управляет пользователями, видит все роли, блокирует любого. **Не имеет доступа к слоям**. |
| `CHIEF` | Руководитель. Создает компании, управляет пользователями внутри компаний. Имеет глобальный доступ (без слоя). |
| `USER` | Обычный пользователь. Имеет доступ только к компаниям, куда его добавили. |

### 3.2. Роли внутри слоя (в `membership.role`)

| Роль | Описание |
|------|----------|
| `chief` | Руководитель слоя. Управляет пользователями внутри слоя. |
| `glavbukh` | Главный бухгалтер. Работает с финансами слоя. |
| `kassa` | Кассир. Работает с кассовыми операциями. |
| `sklad` | Кладовщик. Работает со складскими операциями. |

5. Потоки данных
5.1. Инициализация (первый запуск)
Создаются два пользователя:

super_admin / admin123 (глобальная роль: SUPER_ADMIN)

chief / chief123 (глобальная роль: CHIEF)

Для chief создается запись в membership с tenant_id = NULL и паролем chief123 (глобальный доступ).

Слои не создаются!

5.2. Вход в систему
Алгоритм:

Поиск пользователя в global_users по логину.

Если пользователь найден, поиск всех записей в membership.

Проверка пароля против layer_access_hash в каждой записи.

SUPER_ADMIN — вход без слоя (tenant_id = None).

Если пароль совпал с одной записью:

Если tenant_id = NULL → вход без слоя.

Если tenant_id не NULL → вход в компанию.

Если пароль совпал с несколькими записями → ошибка.

Если пароль не совпал ни с одной записью → ошибка.

5.3. Создание компании
CHIEF входит с глобальным паролем (tenant_id = None).

На дашборде нажимает "Создать компанию".

Заполняет форму: Название, Описание, Пароль.

Система создает:

Запись в tenants_layers.

Запись в membership (user_id = CHIEF, tenant_id = ID компании, role = "chief", пароль = хеш пароля).

Создается новый JWT-токен с tenant_id = ID компании.

Пользователь перенаправляется на дашборд (уже внутри компании).

5.4. Управление пользователями внутри компании
CHIEF входит в компанию (tenant_id = ID компании).

На дашборде нажимает "Управление компаниями".

Видит список пользователей компании.

Может:

Добавить пользователя (выбрать из списка всех USER и CHIEF).

Назначить роль (glavbukh, kassa, sklad, chief).

Заблокировать/разблокировать доступ.

Сбросить пароль (генерация нового пароля).

6. Безопасность
6.1. Пароли
Хеширование паролей через Argon2 (библиотека passlib).

Каждый пароль хранится в отдельной записи membership.

Один пароль не может использоваться для двух компаний одного пользователя.

6.2. JWT-токены
Токен содержит user_id и tenant_id (может быть NULL).

Время жизни токена: 30 минут.

Токен хранится в cookie (httponly).

6.3. Row-Level Security (RLS)
Включен для всех таблиц с tenant_id.

Политика: USING (tenant_id = current_setting('app.tenant_id')::UUID).

Бэкенд устанавливает app.tenant_id при каждом запросе.
